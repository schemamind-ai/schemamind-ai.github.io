Can language models learn database schemas?

A senior research project investigating how much knowledge of an SQL database’s structure a language model can learn through fine-tuning, and what happens to that knowledge when the database changes after training.

About the project

What we are investigating and why it matters.

The problem

Text-to-SQL systems let people ask questions about a database in natural language. A language model translates each question into an SQL query. To write a correct query, the model has to know the structure of the database: which tables exist, what their columns are called, and how the tables are related.

Normally, language models need information about database tables and columns each time they generate a query. Every request therefore carries a description of the database, which can be long for large schemas and must be kept up to date.

Our approach

SchemaMind AI asks how much of this information a model can actually learn during training. We will fine-tune an open-source language model with SQL queries, database schemas, and examples of how tables are related, and compare different training approaches, including LoRA and QLoRA.

Databases change over time. A second part of the project tests what happens when a database changes after the model has been trained, and whether providing updated schema information helps.

Intended contribution

Our goal is to understand when fine-tuning is useful, what its limitations are, and how models can handle changes in database structures. The project is an academic study built on controlled comparisons, together with an application that demonstrates the results. It is not a general-purpose SQL chatbot.

Research questions

Based on the project proposal. They may be refined in later reports.

  1. RQ1

    How much knowledge of a database’s tables, columns and relationships can a language model acquire through fine-tuning?

  2. RQ2

    How do different training approaches, including LoRA and QLoRA, compare with each other?

  3. RQ3

    When a database changes after training, for example when a table or column is renamed, can the model still generate correct SQL queries, and does providing updated schema information help?

  4. RQ4

    How does a fine-tuned model compare with methods that provide database information directly to the model, and when is fine-tuning useful?

Proposed methodology

What we plan to do. Technical choices will be finalised in later reports.

Planned workflow

  1. Select an open-source language model

    The proposal does not fix a specific model. The choice will be made and justified in a later project report.

  2. Prepare training data

    Build training examples from SQL queries, database schemas, and examples of how tables are related.

  3. Fine-tune the model

    Train with parameter-efficient methods. LoRA trains small adapter matrices instead of all model weights; QLoRA applies the same idea to a quantized model to reduce memory use.

  4. Evaluate and compare

    Test the models on SQL datasets such as BIRD and compare them with methods that provide database information directly to the model.

  5. Change the schema and test again

    Modify the database after training, for example by renaming a table or column, and measure whether the model can still generate correct SQL.

Approaches to compare

Schema in the prompt

Planned

A model without database-specific fine-tuning that receives the database schema together with each question. This is the reference point.

Fine-tuned with LoRA

Planned

A model fine-tuned on the database using low-rank adapters.

Fine-tuned with QLoRA

Planned

The same idea applied to a quantized model, compared with LoRA.

Fine-tuned, with updated schema information

Planned

After a schema change, the fine-tuned model is also given information about what changed.

Retrieved schema information

Under consideration

Only the parts of the schema relevant to a question are retrieved and supplied with it.

Fine-tuning combined with schema retrieval

Under consideration

A fine-tuned model that also receives retrieved schema information.

Planned items are stated in the project proposal. Under consideration items are being evaluated by the team and are not part of the project proposal.

Schema changes to test

After a model has been trained, the database is modified and the same questions are asked again. The examples below show the kinds of change involved.

  • Rename a column

    Planned

    Before: customers.name → After: customers.full_name

  • Rename a table

    Planned

    Before: orders → After: purchases

  • Add a table

    Under consideration

    Added: + shipments

  • Change a relationship

    Under consideration

    Before: orders.customer_id → customers → After: orders.account_id → accounts

Comparisons

  • Fine-tuned models compared with methods that provide database information directly to the model, on SQL datasets such as BIRD.
  • LoRA compared with QLoRA.
  • Results before and after each schema change, with and without updated schema information.

Candidate measures

Execution accuracy Under consideration
Whether a generated query returns the same result as a reference query when both are run on the database.
Robustness to schema changes Under consideration
How each approach’s results change after the schema is modified.
Resource requirements Under consideration
The training time and memory each approach needs.
